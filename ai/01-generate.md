# 01. Генерація моделі

## Мій промпт
Ти — аналітик даних. На основі файлу `spec.md` (додається) побудуй ER-модель у Mermaid `erDiagram`.

Вимоги:
- Лише синтаксис Mermaid, без SQL DDL та ORM.
- Сутності й назви полів — рівно як у spec.md.
- Атрибути позначай PK / FK / UK; усі id — тип int.
- Кардинальності — за таблицею зв'язків (розділ 2).
- Чисті M:N — прямий зв'язок без сполучних сутностей. Нотацію кардинальності переноси зі списку «Нотація Mermaid» у spec.md дослівно; власних нотацій не вигадуй. Асоціативна сутність — лише LOAN. 
- Перевір усі критерії AC-1…AC-10 і окремо виведи список порушень, якщо вони є.

## 2. Зв'язки

| # | Зв'язок | Кардинальність | Пояснення |
|---|---|---|---|
| R1 | PUBLISHER — BOOK | 1 : 0..N | видавець випускає 0+ книг; книга має рівно одного видавця |
| R2 | AUTHOR — BOOK | M : N (автор 0..N книг; книга 1..N авторів) | автор написав 0+ книг; книга має 1+ авторів. Без власних атрибутів → зв'язок, не сутність |
| R3 | CATEGORY — BOOK | M : N (0..N з обох боків) | книга належить 0+ категоріям. Без власних атрибутів → зв'язок |
| R4 | BOOK — BOOK_COPY | 1 : 1..N | книга має 1+ примірників; примірник належить одній книзі |
| R5 | READER — LOAN | 1 : 0..N | читач має 0+ видач; видача належить одному читачеві |
| R6 | BOOK_COPY — LOAN | 1 : 0..N | примірник бував у 0+ видачах; видача стосується одного примірника |

Нотація Mermaid:
- R1: PUBLISHER ||--o{ BOOK
- R2: AUTHOR }|--o{ BOOK
- R3: CATEGORY }o--o{ BOOK
- R4: BOOK ||--|{ BOOK_COPY
- R5: READER ||--o{ LOAN
- R6: BOOK_COPY ||--o{ LOAN

## 3. Критерії прийняття

- **AC-1.** Кожна сутність має одноколонковий PK `<сутність>_id` типу `int`.
- **AC-2.** Кожен FK має ту саму назву й тип, що PK, на який посилається.
- **AC-3 (3NF).** Немає похідних атрибутів (напр. статусу «видано/вільно», «прострочено»: вони обчислюються з `LOAN`), немає повторюваних груп, немає транзитивних залежностей (атрибути видавця — лише в PUBLISHER).
- **AC-4.** Чисті M:N (R2, R3) показані як зв'язки між сутностями, без сполучних таблиць.
- **AC-5.** Асоціативна сутність допустима лише там, де зв'язок має власні атрибути: це тільки `LOAN`.
- **AC-6.** Назви сутностей і полів у `model.mmd` збігаються зі `spec.md` буква в букву (перевіряє `scripts/check_consistency.py`).
- **AC-7.** Кардинальності в моделі відповідають таблиці розділу 2, зокрема R2: книга має щонайменше одного автора (`}|--o{`).
- **AC-8.** Усі UK з розділу 1 позначені в моделі як `UK`.
- **AC-9.** Діаграма генерується лише з `model.mmd`; ручні правки рендеру заборонені.
- **AC-10.** Без SQL DDL та ORM — тільки концептуально-логічна ER-модель.

 і у кінці був додан файл `spec.md`

## Мій фідбек
Сутності й поля збігаються з моїм поточним model.mmd, типи й ключі (PK/FK/UK) теж.
Кардинальності: усі шість збігаються зі списком нотації в spec (||--o{, }|--o{, }o--o{, ||--|{, ||--o{, ||--o{). R2 ШІ тепер зробив правильно, бо нотація береться зі spec.
Відрізняються лише підписи зв'язків: у відповіді ШІ categorizes, has, makes, involves, у моєму model.mmd classifies, has copies, borrows, is lent in. Це косметика, на зміст не впливає; скрипт підписів не перевіряє.
Висновок: перегенерація дала ту саму модель, тож виправлений промпт працює і більше не змушує ставити }o--o{ для R2.
